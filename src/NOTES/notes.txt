#engine #core #maps #collision

Maps Parsing

  Two-tier system:                                                      
  - ChunkedLevel for open worlds: streams 30x30-tile chunks via ChunkManager based on camera  
  proximity, with a world.json manifest mapping coordinates to chunk files.                   
  - SimpleLevel for interiors: loads a single Tiled JSON map, no streaming overhead.          
                                                                                              
  TiledChunk parsing:                                                     
  - Layers split into ground/collision/foreground by convention
  - Static layers pre-rendered to offscreen canvas (good perf win)
  - Animated tiles supported natively
  - Collision encoded as bit-packed coordinates in a Set for O(1) lookups

  Potential concern: No spatial indexing beyond the collision set. As object counts grow,
  finding nearby entities is still a linear scan.


  Render pipeline in Main.js:
  1. Clear → camera transform → ground layers → Y-sorted objects → foreground layers → HUD

  Key optimizations already in place:
  - Dirty-flag Y-sorting: _ySortDirty flag avoids re-sorting every frame
  - Viewport culling: objects and tiles outside view are skipped
  - HUD caching: rendered to offscreen canvas, only redrawn when _hudDirty
  - Static layer caching: ground/foreground pre-baked

  Potential concern: No render batching — each sprite is an individual drawImage call. Fine
  for current scale, but would become a bottleneck with many on-screen objects.

#engine #sprites #collision
The "tile reservation" subtlety:
That destinationPosition ?? position is significant. While a character interpolates between tiles, its collision footprint is at the destination tile, not the visual position. So if Hero is at (5,5) moving to (6,5), an enemy trying to enter (6,5) is blocked from the moment Hero commits — not when Hero visually arrives.

This is a reservation model. The character "owns" the tile it's heading toward. It prevents two characters from interpolating into the same tile and visually overlapping mid-move.

TODO — elevation consumer (parser already in place)
Tiled tile layers with a layer-level `elevation` property (e.g. "Stairs" layer
with elevation: 4) are parsed into a per-tile elevation map. Lookup is exposed
all the way up via `level.getElevationAt(x, y)`. NOTHING currently reads it
on the consumer side — decide later how to use it.

Parser surface (all wired, all working):
  - TiledChunk._registerElevationLayer + getElevationAt
  - ChunkManager.getElevationAt
  - ChunkedLevel.getElevationAt
  - SimpleLevel.getElevationAt

Two design candidates already explored (both reverted, pick one or invent another):

  (A) Visual lift — offset body.position.y by elevation, smoothly lerped.
      Mechanism: per-move target set in MovingState.enter via a
      Character.updateElevationFromTerrain() helper; Character.step lerps
      `elevation` toward `elevationTarget` and writes
      `body.position.y = _bodyRestY - elevation`. Pretty, but no gameplay
      effect.

  (B) Speed slowdown — halve `this.speed` while on or moving toward a stair.
      Mechanism: per-move check in MovingState.enter via a
      Character.updateSpeedFromTerrain() helper; uses `_baseSpeed` to
      restore. Gameplay-meaningful but invisible.

  (C) Both — visual lift + speed slowdown. Probably the most satisfying
      "climbing" feel. Cost: a few extra lines in step() and the helper.

Notes:
  - Whatever consumer ships, the lookup is `level.getElevationAt(x, y)`.
    `x, y` are world-space pixel coords matching the tile anchor (same
    coordinate system as `position` / `destinationPosition`).
  - The natural call site is `MovingState.enter()` (per-move, applies to
    all Characters, not just the player). Adding the check in
    PlayerController.tryMove would make it player-only.
  - For knockback effects on stairs: HitState uses its own KNOCKBACK_SPEED
    and doesn't read character.speed, so option (B) wouldn't affect
    knockback through a stair. Option (A) would (body lifts during the
    knockback move).

#stateMachine #state

Behavior now:
up-down-attack (move first, then attack): hero finishes UP move → faces DOWN → attacks DOWN.
up-attack-down (attack first, then move): hero finishes UP move → attacks UP (original facing). DOWN is dropped on attack start.
up-down-left-attack: hero finishes UP move → faces LEFT (latest move-buffer value) → attacks LEFT.
up-move-only (no attack): unchanged — tryMove picks it up on next IDLE tick.

*the trick: if both movement and attack are buffered, then if movement is first, then transform it to change in facing direction. if movement is second, then digest it and fire buffer only attack.

#combat #enemies #pathfinding
1. Shared registry (minimum change). Add a static EnemyRegistry (a Set<Enemy>) — each enemy registers on spawn and removes on destroy. The controller queries EnemyRegistry.others(this) to get the small list of fellow enemies, no scene scan. Fast, but pinch-attack logic still lives in EnemyController and each enemy re-derives its role every tile (with risk of three enemies disagreeing on who's on the left flank).

2. Squad object (more structured, what I'd recommend). A Squad holds direct refs to N enemies and assigns roles (flank-left, flank-right, front). Each enemy reads this.squad.role(this) and the desired target tile. Enemies are dumb executors; the squad owns the tactic. Avoids re-derivation, makes it trivial to add new formations (envelop, line, scatter) without growing the controller, and one place to fix when behavior is wrong.

Tradeoff: Squad is a new abstraction that needs spawning (Tiled object layer with a squadId property → factory groups enemies into a Squad). Registry is just one file but the "who plays which role" decision still has to live somewhere — it usually grows into a squad anyway.

#collision #performance #tiled
Option A for static-vs-dynamic solids: tag each Tiled object layer with a custom property `static: true|false` (e.g. Chests/Signs/Fences = static, Npcs/Enemies = dynamic). Factory reads the layer prop when spawning and stamps each object with a flag (e.g. `isStatic`). ChunkedLevel's blockers cache then bakes any `isSolid && isStatic` object's tile into the walls Set on spawn (and clears it on destroy via a walk-up like the YSort cleanup). isTileFree's children scan only checks objects without the flag — Characters and other dynamic solids.

Win: removes the per-call O(N) scan over static solids; helpers stay decoupled from the Character class (no instanceof in grid.js). Tradeoff: another piece of layer metadata that has to stay in sync — wrong default on a new layer is an easy mistake. Pick a sensible default (probably `static: false` so dynamic is the safe fallback). For instance-level overrides (e.g. a Chest on a moving platform), put a per-object `static` property on top of the layer default.

Today the walls cache is the only optimization in place; this is the path to take if/when per-call cost in isTileFree becomes measurable (lots of static props + many ranged enemies + projectiles).
